# NOVA Messenger — обязательные правила разработки

## 1. Гостевые аккаунты и переписка
- Гость получает уникальный ник `nova1`, `nova2`, `nova3` и т. д.
- Гость может искать пользователей, отправлять и принимать заявки в друзья, создавать личный чат с другом, писать и получать обычные текстовые сообщения, а также совершать аудиозвонки.
- Гость не может создавать группы, отправлять подарки, загружать медиа, редактировать полный профиль или использовать Premium-функции.
- Запрещено блокировать текстовые сообщения и аудиозвонки только по признаку `auth.currentUser.isAnonymous === true`.
- Перед отправкой текста проверять, что пользователь вошёл в NOVA, открыт чат и его UID присутствует в `chats/{chatId}/members`. Показывать исходную ошибку Firebase, если запись отклонена.
- Гостю можно писать только в существующий личный чат с участником. Если чата нет, сначала нужно создать его через добавление в друзья/принятие заявки.
- При регистрации из гостевого профиля привязывать email/пароль к текущему anonymous-пользователю через `linkWithCredential`, чтобы сохранить UID, ник, друзей и историю чатов.
- Не удалять и не заменять гостевой профиль при обычном обновлении APK.

## 2. Firebase и безопасность
- Не публиковать открытые правила вида `.read: true` или `.write: true`.
- Для сообщений разрешать чтение/запись только участникам соответствующего чата; при записи проверять `senderUid === auth.uid`. Это правило одинаково для зарегистрированных и анонимно авторизованных пользователей Firebase.
- Для звонков разрешать сигналинг только участникам звонка. Гость должен иметь право создать звонок, если он является участником чата и входит в `members) звонка.
- Не доверять ограничениям только в интерфейсе: защищать данные правилами Realtime Database.
- После изменения `docs/firebase-database-rules.json` обязательно вручную опубликовать правила в Firebase Console → Realtime Database → Rules. Коммит в GitHub сам по себе правила Firebase не применяет.
- В Firebase Authentication должны быть включены **Email/Password** и **Anonymous**. Если регистрация не работает, проверить эти провайдеры и раздел Authorized domains.
- Не просить пользователя делать базу публичной для исправления ошибок доступа.

## 3. Android APK — обязательные критерии готовности
- APK не считается рабочим только потому, что Gradle собрал файл.
- Android workflow должен добавлять `INTERNET`, `ACCESS_NETWORK_STATE`, `RECORD_AUDIO`, `MODIFY_AUDIO_SETTINGS` и `CAMERA` в AndroidManifest до сборки.
- При звонке запрашивать системное разрешение на микрофон; для видеозвонка также на камеру. Если WebView не поддерживает `navigator.mediaDevices.getUserMedia`, показывать понятную ошибку, а не молча завершать звонок.
- Перед публикацией APK вручную проверить на физическом Android-устройстве:
  1. Регистрация email/пароль и повторный вход.
  2. Гостевой вход с уникальным ником.
  3. Поиск пользователя, заявка в друзья, принятие заявки и создание личного чата.
  4. Отправка и получение текста между двумя аккаунтами.
  5. Исходящий и входящий аудиозвонок между двумя устройствами.
  6. Разрешения микрофона и камеры.
  7. Сохранение входа после закрытия и повторного запуска приложения.
- При ошибке сохранять исходный Firebase/Auth/WebRTC код в console/logcat и показывать пользователю полезное сообщение.

## 4. Правила исправлений
- Сначала исправлять регистрацию, вход, гостевой режим, текстовые сообщения и аудиозвонки; только потом добавлять новые функции.
- После изменения Firebase/Auth/calls проверять одновременно Windows и Android.
- Не удалять рабочие функции ПК при исправлении Android.
- Исправлять первопричину; не скрывать ошибки и не обходить безопасность базы.
- В описании релиза честно указывать, какие проверки реально пройдены; успешная сборка не равна успешному тесту приложения.
